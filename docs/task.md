# როტაციის კალკულატორის შექმნის დავალება Claude Code აგენტების გუნდისთვის

დავალების მომზადების თარიღი: 2026 წლის 28 ოქტომბერი

შენ ხარ Claude Code-ის აგენტების გუნდის ხელმძღვანელი. შექმენი ქართულენოვანი როტაციის კალკულატორი საქართველოს საგარეო საქმეთა სამინისტროს მოსამსახურეთა გრძელვადიანი სამუშაო მივლინების თანხისა და დაკავშირებული ხარჯების გასაანგარიშებლად. საფუძვლად გამოიყენე თანდართული ბრძანება №01-82, მისი ათივე დანართი და არსებული HTML კალკულატორი. ქვეყნისა და ქალაქის არჩევისას მომხმარებელს იქვე აჩვენე ცენტრში ბინის ქირის საორიენტაციო თვიური ფასი და ცხოვრების ღირებულების ინდექსი სანდო, ნებადართული მონაცემთა წყაროდან.

ჩემი მთავარი პრიორიტეტებია გამოთვლების სისწორე, მარტივი ქართული ინტერფეისი და მარტივი გამოყენება. სასურველია საბოლოო პროდუქტი იყოს ერთი HTML ფაილი, რომელიც ბრაუზერში ორმაგი დაწკაპუნებით იხსნება. თუ ავტომატურად განახლებადი ფასებისთვის საჭიროა სერვერული ნაწილი, მოამზადე Cloudflare-ზე გასაშვებად გამზადებული პროექტი. მხოლოდ გეგმით ან მაკეტით არ შემოიფარგლო: შექმენი კოდი, გადაამოწმე და მომაწოდე გამოსაყენებელი ფაილები.

## 1 მუშაობის წესი და გუნდი

შექმენი ერთი ხელმძღვანელისა და ხუთი სპეციალიზებული აგენტის გუნდი. რეალურად გამოიყენე ხელმისაწვდომი Agent Teams ან subagents ფუნქციები. გუნდური მუშაობის სიმულაციას ერთ პასუხში ნუ წარმოადგენ რეალურ მრავალაგენტიან შესრულებად. თუ Agent Teams ამ გარემოში მიუწვდომელია, გამოიყენე subagents და მიუთითე ეს განსხვავება. იმუშავე ეტაპებად, რათა ურთიერთდამოკიდებული ამოცანები პარალელურად არ დაიწყოს ნაადრევად.

ფაილის კონკრეტულ ცვლილებას ერთდროულად ჰყავდეს ერთი მფლობელი. საერთო ტიპების ცვლილებები შეთანხმდეს ხელმძღვანელთან. საჭიროებისას გამოიყენე იზოლირებული სამუშაო ასლები ან git worktrees; აგენტებმა ერთმანეთის ცვლილებები არ გადაწერონ. პასუხისმგებლობების გადანაწილებისას განაახლე დავალებების სია.

დამოუკიდებელმა შემმოწმებელმა მოსალოდნელი თანხები წესებიდან გამოთვალოს. იმავე ფუნქციის შედეგის გადაწერა ტესტის მოსალოდნელ მნიშვნელობად ვალიდაცია არ არის. აგენტების როლები არ ნიშნავს, რომ სამართლებრივი ინტერპრეტაცია ავტომატურად უწყებრივად დამტკიცებულია.

რუტინული ტექნიკური გადაწყვეტილებები მიიღე დამოუკიდებლად. თუ API გასაღები, გადახდილი ლიცენზია ან კონკრეტული სამართლებრივი განმარტება არ გაქვს, დაასრულე დანარჩენი სამუშაო, მიუთითე ზუსტად შეზღუდული ნაწილი და უზრუნველყავი გამოსადეგი ალტერნატიული რეჟიმი. გადახდილი სერვისი არ გამოიწერო და რეალურ ანგარიშზე პროექტი არ გამოაქვეყნო ცალკე მითითების გარეშე. ეს დავალება მოიცავს განთავსებისთვის კოდის მომზადებას.

თავდაპირველი სამუშაო საფუძველია მოწოდებული დოკუმენტების ნაკრები. HTML არის პროტოტიპი და შესადარებელი კოდი; მასში ჩაწერილი მონაცემი სამართლებრივ წყაროს ვერ ჩაანაცვლებს. ოფიციალურ წყაროში მოძიებული უფრო ახალი რედაქცია ცალკე აღრიცხე და შეუსაბამე მოქმედების თარიღებს. სხვადასხვა პერიოდის ნორმები უხმოდ არ შეურიო.

2026 წლის 28 ოქტომბერს მაცნეს საჯარო გვერდზე ჩანდა კონსოლიდაციის თარიღი 13/08/2026, მაგრამ სრული კონსოლიდირებული ტექსტი ავტორიზაციას მოითხოვდა და საჯაროდ ნაჩვენები ტექსტი პირველადი რედაქცია იყო. ამიტომ საჯარო გვერდზე გახსნილი ძველი თანხებით არ გადაწერო მოწოდებული განახლებული დანართები. მიუთითე რას ამოწმებ: მოწოდებულ რედაქციას, საჯაროდ ხელმისაწვდომ ცვლილებას თუ სრულ მოქმედ კონსოლიდაციას. წვდომის გარეშე ბოლო რედაქციის სრული გადამოწმება დასრულებულად არ მონიშნო.

`.doc` გაფართოება ყველა ფაილში ერთ ფორმატს არ ნიშნავს: `(10)(1).doc` რეალურად DOCX-ის კონტეინერია, დანარჩენები ძველი Word-ის ფაილებია. გამოიყენე შიგთავსის ამოცნობა და საჭიროების შემთხვევაში LibreOffice-ის კონვერტაცია. შეინარჩუნე დედნები; ცხრილები გადაამოწმე ვიზუალურადაც, განსაკუთრებით გაერთიანებული უჯრების, ათწილადი მძიმის, დუბლირებული ტექსტისა და წაშლილი სტრიქონების შემთხვევაში.

შექმენი წყაროების რეესტრი: ფაილის სახელი, SHA-256, დანართი, რედაქციის შესახებ რეალურად ცნობილი ინფორმაცია, მოპოვების თარიღი და შეზღუდვები. ფაილის შექმნის ან ბოლო შენახვის თარიღი ნორმის ამოქმედების თარიღად არ გამოიყენო.

თითოეულ სამართლებრივ წესსა და მონაცემს მიაბი წყარო: ბრძანების პუნქტი ან დანართის ნომერი, მუხლი, ცხრილის სტრიქონი და საჭიროებისას გვერდი. წესის რეესტრში ჰქონდეს `ruleId`, აღწერა, წინაპირობა, ფორმულა, გამონაკლისი, წყარო და დაკავშირებული ტესტები. გაურკვეველი ამოქმედების თარიღი დატოვე უცნობად; ნუ გამოიცნობ.

## 4 ფინანსური ბირთვი

ფინანსური ბირთვი უნდა იყოს სუფთა ფუნქციების ერთიანი მოდული, რომელიც მუშაობს DOM-ის, ქსელისა და სერვერის გარეშე. ორივე გამოსაშვები ვერსია ერთსა და იმავე გამოთვლებს იყენებდეს. Numbeo-სა და სხვა ბაზრის მონაცემები ამ მოდულის სამართლებრივ პარამეტრებს არ ცვლიდეს.

### ძირითადი ფორმულები

მოწოდებული რედაქციის მიხედვით, ბრძანების მე-3 პუნქტში საბაზისო თანხებია `H_EUR = 3100` და `H_USD = 3495`. ოჯახზე დანამატი არის 7%. წყარო: დანართი №1, მუხლი 3.

```text
D = H × (A_percent / 100) × K × (1 + 0.07 × C)
T = D × (E_percent / 100)
S = D − T + F
```

აქ `C` არის კონკრეტული პერიოდისთვის დანამატის მიღების უფლების მქონე ოჯახის წევრთა რაოდენობა, მოსამსახურის გარეშე. `A`-ს ან `E`-ს პროცენტი მხოლოდ ერთხელ უნდა გადაიყვანო წილადში.

ბინის თვიური ქირა არის `G`. სრული თვისთვის:

```text
G = 0:
    F = 0

0 < G < T:
    F = T

G > T, ხელმძღვანელი:
    additionalRentCompensation = min(0.80 × (G − T), 2 × T)
    F = T + additionalRentCompensation

G > T, სხვა მოსამსახურე:
    additionalRentCompensation = min(0.50 × (G − T), T)
    F = T + additionalRentCompensation
```

ხელმძღვანელის შემთხვევაში 200%-იანი ზღვარი ეხება დამატებით ნაწილს; შესაბამისად `F` მაქსიმუმ `3T` შეიძლება იყოს. სხვა მოსამსახურისთვის `F` მაქსიმუმ `2T` არის. არ შეზღუდო მთლიანი `F` შეცდომით `2T`-ით ან `T`-ით.

`G = T` შემთხვევა დანართის ტექსტში ცალკე ჩამოყალიბებული არ არის. შემოთავაზებული უწყვეტი მათემატიკური გადაწყვეტაა `F = T`. სამართლებრივი წესების ანალიტიკოსმა ეს ინტერპრეტაციად აღრიცხოს და გადაამოწმოს; არ წარმოადგინოს პირდაპირ ციტირებულ ცალკე ნორმად. აშკარა არითმეტიკული გაგრძელების გამო დანარჩენი პროექტი არ გააჩერო.

`G = 0` ნიშნავს ნამდვილად არარსებულ ქირას. ცარიელი ველი ნიშნავს, რომ ქირა ჯერ უცნობია. უცნობი ქირისას აჩვენე დამოუკიდებლად გამოთვლადი ნაწილი და სრული შედეგისთვის საჭირო მონაცემი. ქირა არ არის სავალდებულოდ ბაზრის საშუალოს ტოლი.

თუ `0 < G < T`, არ შეცვალო `F = T` „ლოგიკური გამარტივებით“ `F = G`-ად. ბინის ხარჯის დაუფარავი ნაწილი აჩვენე როგორც `max(G − F, 0)`, ხოლო `F − G` დადებითი სხვაობა საჭიროებისას ცალკე განმარტე.

### თანამდებობა და სპეციალური სტატუსი

№2 და №3 დანართები წარმოადგინე ორ დამოუკიდებელ რეჟიმად. ერთი და იმავე თანამდებობის სახელს განსხვავებული პროცენტი შეიძლება ჰქონდეს: მაგალითად მეორე მდივანი №2-ში 60%-ია, №3-ში 55%. №3-ის გამოყენებას მიაბი ბრძანების 37–39-ე პუნქტებით გათვალისწინებული პირობები.

ხელმძღვანელის სტატუსი არ გამოიცნო მხოლოდ მაღალი თანამდებობრივი პროცენტით. განასხვავე თანამდებობრივი მაჩვენებელი და ქირისთვის/საკომისიოსთვის მოქმედი სტატუსი. ტიპური ხელმძღვანელი თანამდებობებისთვის შესთავაზე სწორი მნიშვნელობა, ხოლო მოვალეობის შესრულების სპეციალურ შემთხვევებს მიაბი სამართლებრივი საფუძველი.

ბრძანების 20, 20¹ და 20² პუნქტები გაითვალისწინე ცალკე: დროებითი ფუნქცია ზოგადად ავტომატურად არ ცვლის განაკვეთს; სპეციალური შემთხვევები შესაბამის პირობებსა და აქტს უნდა ეფუძნებოდეს. 2026 წლის ცვლილებით გათვალისწინებული ადმინისტრაციული მენეჯერის 75%-იანი მაჩვენებელი არ დაკარგო.

- ერთი ოჯახის ხარჯზე ორმაგი დაფინანსება თავიდან აიცილე. სხვა უწყებიდან ანაზღაურების ფაქტი საჭირო ხარჯებისთვის ცალკე იკითხე.
- პირველადი მოწყობისთვის დასათვლელი წევრების რაოდენობა არ გააიგივო ყოველთვიური 7%-იანი დანამატის რაოდენობასთან.

- შესაბამისი პირების ქვეყანაში ყოფნის დღეები და ოჯახის შემადგენლობის ცვლილების თარიღი იმ წესებისთვის გამოიყენე, რომლებზეც ეს პირობა ვრცელდება.

ერთი checkbox-ით „ოჯახის წევრია“ ყველა სახის ანაზღაურების უფლება ავტომატურად არ მიანიჭო.

### პერიოდები და სიზუსტე

ძირითადი რეჟიმი იყოს სრული თვის შეფასება. დამატებით უზრუნველყავი თარიღებით გაანგარიშება, არასრული თვეები და შუა თვეში ქირის ან ოჯახის შემადგენლობის ცვლილება. დანართი №1 ითვალისწინებს კალენდარული დღეების რაოდენობასა და ცვლილების თარიღიდან გადაანგარიშებას.

თვის მონაკვეთისთვის ჯერ გამოთვალე სრული თვიური განაკვეთი შესაბამისი მონაცემებით, შემდეგ გამოიყენე დასაბუთებული დღიური პროპორცია და შეაჯამე მონაკვეთები. არ გაამრავლო ოჯახის დანამატი ან ქირის შეზღუდვა ორჯერ ნაწილობრივი პერიოდით. სხვადასხვა თვეს თავისი 28, 29, 30 ან 31 დღე ჰქონდეს. თარიღები დაამუშავე კალენდარულ თარიღებად, დროის სარტყლის ან DST-ის გამო დღის დაკარგვის გარეშე.

არ მოიგონო წესები, რომლებიც წყაროში არ წერია: მაგალითად დაზღვევის წლიური ლიმიტის ავტომატური პროპორცირება, ასაკის ჯგუფის ცვლილების საანგარიშო თარიღი ან შვებულების დანამატის წლიურ ჯამში დამატებით ჩათვლა. ასეთ საკითხზე ჩაიწეროს დასაბუთებული მიდგომა ან კონკრეტული დაუზუსტებელი პირობა. არასრული ინფორმაცია არ ჩაანაცვლო ნულით.

გამოიყენე დეტერმინისტული ათწილადი ან რაციონალური არითმეტიკა. შუალედური მნიშვნელობების გამეორებითი დამრგვალება თავიდან აიცილე. საჩვენებელი თანხები ძირითადად ორ ათწილადამდეა; საანგარიშო დამრგვალების პოლიტიკა აღწერე და ტესტით დააფიქსირე. თუ სამართლებრივ წყაროში დამრგვალების ცალკე წესი არ არის, ტექნიკური პოლიტიკა ნორმად არ მონიშნო.

დაფინანსების ვალუტა აიღე №5/№6 დანართიდან და არა ქვეყნის ადგილობრივი ვალუტიდან ან ევროზონის წევრობიდან. ბრძანების მე-2 პუნქტში მოწოდებულია საპროგნოზო კურსები: 1 USD = 2.8 GEL და 1 EUR = 3.2 GEL; ამავე პუნქტში დაფინანსება დაკავშირებულია დაფინანსების დღის გაცვლით კურსთან. განასხვავე საპროგნოზო კურსი, დაფინანსებისთვის გამოსაყენებელი კურსი და ბაზრის ფასის საჩვენებელი კონვერტაცია. Numbeo-ს კურსი უწყების საანგარიშსწორებო კურსად არ გამოაცხადო. GEL ეკვივალენტის ჩვენებისას მიაწერე გამოყენებული კურსი, თარიღი და დანიშნულება.

## 5 განათლება დაზღვევა და სხვა ხარჯები

### განათლება

უფლებამოსილი ბავშვისთვის დასაშვები ხარჯი `P` და შესაბამისი თვიური ზღვარი `L`:

```text
L_EUR = 690
L_USD = 750
educationReimbursement = min(P, L) + 0.80 × max(P − L, 0)
personalEducationCost = P − educationReimbursement
```

გადაამოწმე თითო ბავშვზე გამოყენების საფუძველი და აღწერე. არ გააერთიანო სხვადასხვა ბავშვის ხარჯები ერთ ზღვარში დაუდასტურებელი ვარაუდით. წყარო: ბრძანების 31–36-ე პუნქტები და დასასრულის შენიშვნა.

ცალკე გაითვალისწინე სწავლა, რეგისტრაცია, ნებადართული ტრანსპორტირება და კვება; სასწავლო წლის პერიოდი; არდადეგებზე დამატებითი ხელშეკრულების შეზღუდვა; სახელმწიფო ენაზე უფასო სასწავლებლის არსებობასთან დაკავშირებული პირობა; ინდივიდუალური გადაწყვეტილებით დაშვებული გამონაკლისები. წლიური რეგისტრაციის საფასურის თვეებზე განაწილების დაუდგენელი წესი თვითნებურად არ შექმნა.

### დაზღვევა

№7 და №8 დანართებიდან ამოიღე ყველა დაწესებულების ყველა ასაკობრივი უჯრა. გამოიყენე დასახელება/სტაბილური ID და არა ერთმანეთთან შემთხვევით დამთხვევადი მასივის ინდექსები.

ასაკობრივი ჯგუფებია 0–18, 19–24, 25–29, 30–34, 35–39, 40–44, 45–49, 50–54, 55–59, 60–64, 65–69 და 70+. ოჯახის წევრის ცარიელი ასაკი არ მიაკუთვნო 0–18 ჯგუფს. 70+ ჯგუფი აუცილებლად იყოს მხარდაჭერილი.

აჩვენე თითო პირისთვის წლიური ზღვარი, ფაქტობრივი/დაგეგმილი პოლისის ფასი, შესაბამისი პერიოდი, ანაზღაურება და საკუთარი ხარჯი. ერთსა და იმავე წლიურ ლიმიტზე რამდენიმე ხარჯის შემთხვევაში გაითვალისწინე უკვე გამოყენებული თანხაც. უფლებამოსილებისა და პერიოდის პირობები მოდის ბრძანების 30-ე პუნქტიდან; წლიური ლიმიტი ყოველთვიურ ან ერთჯერად თავისუფალ შემოსავლად არ აქციო.

### პირველადი მოწყობა

ბრძანების მე-7 პუნქტის მიხედვით:

```text
settlementAllowance = dailyRate × 60 × (1 + 0.10 × eligibleSettlementFamilyCount)
```

მხარდაჭერის მიმღები და მეურვეობის/მზრუნველობის ქვეშ მყოფი პირები ამ 10%-იან დანამატში არ შედიან. დაამუშავე მე-9 პუნქტის გამონაკლისები და მე-10 პუნქტით გათვალისწინებული სხვა ქალაქში გადაყვანა.

კრიტიკული დამატებითი წყაროა მთავრობის 2017 წლის 25 აპრილის №211 დადგენილების შესაბამისი რედაქციის №1 დანართი. ის მოწოდებულ 12 ფაილში არ არის. ძველ HTML-ში ჩაწერილი `dsa` მნიშვნელობები დაუდასტურებელია, სანამ შესაბამის წყაროს არ შეადარებ. მოძებნე ოფიციალური მოქმედი/საანგარიშო პერიოდის წყარო; თუ ვერ მიიღებ, უზრუნველყავი ხელით შეყვანა წყაროსა და თარიღის მითითებით და მონიშნე, რომ ნორმა დადასტურებას საჭიროებს. დაუდასტურებელი თანხა დადასტურებულ საბოლოო ჯამში არ შეიტანო.

`dailyRate`-ს ჰქონდეს საკუთარი ვალუტა. იგი ავტომატურად არ გააიგივო მისიის EUR/USD დაფინანსების ვალუტასთან. სხვა ვალუტის შემთხვევაში აჩვენე კონვერტაციის კურსი, თარიღი, წყარო და სტატუსი. დაუდგენელი კურსით სხვადასხვა ვალუტა არ შეკრიბო.

### მაკლერის მომსახურება

ჩვეულებრივ რეჟიმში, უფლებამოსილების დაკმაყოფილებისას:

```text
brokerReimbursement = min(actualBrokerFee × applicableRate, monthlyRent)
applicableRate = 0.80 for an eligible head, otherwise 0.50
```

მოითხოვე საკომისიოს თანხა, მომსახურების თარიღი, როტაციის დაწყების თარიღი და უკვე მიღებული ანაზღაურების შესახებ ინფორმაცია. გაითვალისწინე წარგზავნიდან ექვსი თვე, ერთჯერადობა და დამადასტურებელი დოკუმენტი. სპეციალური გადაწყვეტილების რეჟიმი მიაბი ბრძანების 8¹ პუნქტს. `actualBrokerFee` ქირის ტოლი ნაგულისხმევად არ იყოს.

### ბარგი და მგზავრობა

ბარგზე გამოიყენე ფაქტობრივი დასაშვები ხარჯი და №9/№10-ის შესაბამისი ზღვარი. ეს არის მოსამსახურისა და ოჯახის ჯამური ზღვარი შესაბამისი შემთხვევისთვის; თითო წევრზე სრულად არ გაამრავლო. განცალკევებულ მოთხოვნებზე შეინახე დარჩენილი ლიმიტი. გამგზავრება, გამოწვევა და უკვე ანაზღაურებული სპეციალური გამოძახება ერთმანეთისგან განასხვავე ბრძანების 4–5² პუნქტების მიხედვით.

მგზავრობაზე შეიტანე ფაქტობრივი ეკონომკლასის ღირებულება, საჭირო შესადარებელი ბილეთის ფასი, მარშრუტი და ხარჯის კატეგორია. პირადი ავტომანქანით მგზავრობის შემთხვევა მე-5 პუნქტის წესით დაამუშავე და ოჯახის ყველა მგზავრზე ბილეთის კომპენსაცია ავტომატურად არ გაამრავლო. შვებულების მგზავრობისთვის გაითვალისწინე 12–17-ე პუნქტები და შესაბამისი წლიური შეზღუდვები.

### ავანსები და განსაკუთრებული ხარჯები

ავანსი წარმოადგენს დასაბრუნებელ თანხას. ბინის ქირის ავანსისთვის აჩვენე თანხა, ჩვეულებრივ რეჟიმში ექვსთვიანი ზღვარი/დაბრუნების ვადა, ყოველთვიური დაფარვა და დარჩენილი ვალდებულება. 22–27-ე პუნქტების გამონაკლისები მონიშნე ინდივიდუალური აქტის მოთხოვნით. ავანსი არც შემოსავლისა და არც ხარჯის ანაზღაურების ჯამში არ აურიო.

ბრძანებაში გათვალისწინებული ვიზა, სავალდებულო ვაქცინაცია, შესაბამისი ტესტირება/კარანტინი, სამსახურებრივი ავტომანქანის ფასიანი გზა/პარკინგი და ადრეული გამოწვევით ხელშეკრულებების შეწყვეტის ხარჯები დაფარე დამატებითი ხარჯების განყოფილებით. თუ ფორმულა არ არსებობს, შეიყვანოს ფაქტობრივი თანხა, კატეგორია და დასაბუთება. მინისტრის გადაწყვეტილებაზე დამოკიდებული ხარჯი checkbox-ის მონიშვნით ავტომატურად დასამტკიცებელ უფლებად არ იქცეს.

შექმენი ყველა პუნქტის დაფარვის სია: ავტომატური გამოთვლა, პირობითი/ხელით შესატანი შემთხვევა, საინფორმაციო წესი ან გამოთვლასთან დაუკავშირებელი დებულება. გაუთვალისწინებელი პუნქტები ჩუმად არ გამოტოვო.

## 6 მისიისა და ქალაქის მონაცემები

სამი ცალკე არსება შექმენი: სახელმწიფო, ქალაქი და დაწესებულება. ოფიციალური საფინანსო მონაცემები მიაბი დაწესებულების ID-ს, ბაზრის მონაცემები კი რეალურ ქალაქსა და პროვაიდერის ქალაქის ID-ს.

- ერთი ქვეყნის რამდენიმე ქალაქი და ერთი ქალაქის რამდენიმე დაწესებულება მხარდაჭერილი იყოს.
- ქალაქის სპეციალური K/E სტრიქონი ქვეყნის ზოგად სტრიქონზე პრიორიტეტული იყოს, როცა წყარო ამას ადგენს; მაგალითად აშშ-ის ქალაქები და ბარი.
- ქართული და ინგლისური სახელები, ალტერნატიული დაწერილობა, ISO ქვეყნის კოდი და საჭიროებისას რეგიონი/შტატი შეინახე ცალკე.
- ბაზრის API-ში ქართული დიპლომატიური დაწესებულების გრძელი დასახელება ქალაქის სახელად არ გაგზავნო.
- NATO/EU/UN მისია შესაბამის ადგილსამყოფელ ქალაქს დაუკავშირე. არ გამოგრჩეს პარიზისა და სტრასბურგის, ვაშინგტონისა და ნიუ-იორკის, ბერნისა და ჟენევის განსხვავება.
- მხოლოდ ქვეყნის არჩევისას, თუ ერთზე მეტი შესაბამისი ქალაქია, ჯერ ქალაქი აირჩევა. ერთი დადასტურებული ქალაქის შემთხვევაში შეიძლება ავტომატური არჩევა, ხილული ქალაქის სახელით.
- ქვეყნის საშუალო მონაცემი ქალაქის ცენტრის ქირად არ აჩვენო. ცალკე აღნიშნე თუ ინფორმაცია ქვეყნის დონეზეა.
- ვატიკანისა და სხვა სპეციფიკური შემთხვევებისთვის გამოიყენე დადასტურებული ფაქტობრივი ადგილმდებარეობა. ახლომდებარე ქალაქის მონაცემი გამოჩნდეს მხოლოდ მკაფიო ახსნით; „ზუსტი დამთხვევის“ სტატუსი არ მიენიჭოს.
- თუ ქალაქი საბაზრო წყაროში არსებობს, მაგრამ ნორმატიული ფინანსური მონაცემი არა, ბაზრის ბლოკი შეიძლება მუშაობდეს; ოფიციალური თანხა დარჩეს დაუდგენელი. ეს ორი მდგომარეობა ერთმანეთისგან დამოუკიდებელია.

## 7 ქირისა და ცხოვრების ღირებულების ბლოკი

ქვეყნის/ქალაქის არჩევისთანავე, ფორმის იმავე ნაწილში აჩვენე ბაზრის მოკლე ბლოკი. მის სანახავად მომხმარებელს შედეგების ბოლო ეტაპზე გადასვლა არ სჭირდებოდეს. ქსელის პასუხის მოლოდინში კალკულატორი გამოსაყენებელი დარჩეს.

### ქირა

საწყისი არჩევანი იყოს „ცენტრი — 1 საძინებელი“. დამატებით შესთავაზე „ცენტრი — 3 საძინებელი“, თუ პროვაიდერს აქვს შესაბამისი მონაცემი. შესაძლებელი იყოს გარეუბნის მონაცემის არჩევაც, მაგრამ ცენტრი დარჩეს ნაგულისხმევად.

„ერთი საძინებელი“ არ თარგმნო „ერთოთახიანად“. წყარო თუ კონკრეტულ ხარისხს არ ადგენს, მიუთითე „ცენტრში ბინის საშუალო საორიენტაციო ქირა“ და მოკლე განმარტება, რომ ბინის ხარისხი, ფართობი, ავეჯი და უბანი განსხვავდება. სტატისტიკური საშუალო ვერ უზრუნველყოფს „საშუალო ხარისხის“ ერთგვაროვან გარანტიას. 2-საძინებლიანის მონაცემი არ გამოიგონო 1-სა და 3-ს შორის ინტერპოლაციით.

აჩვენე საშუალო თვიური ფასი, ვალუტა, პროვაიდერის დიაპაზონი თუ ხელმისაწვდომია, ქალაქი, წყარო, განახლების ცნობილი პერიოდი და მონაცემის სტატუსი. დიაპაზონი არ დაარქვა ნდობის ინტერვალს, თუ პროვაიდერი ასე არ განსაზღვრავს.

ღილაკი „გამოვიყენო დაგეგმილ ქირად“ მომხმარებლის მოქმედებით გადაიტანს თანხას `G`-ში. ასეთ შემთხვევაში გაანგარიშება მონიშნე სცენარად, საბაზრო შეფასებაზე დაფუძნებული ქირით. უკვე შეყვანილი ფაქტობრივი ქირა ქალაქის შეცვლამ ან API-ის განახლებამ უხმოდ არ გადაწეროს; სხვადასხვა ქალაქიდან დარჩენილ ქირაზე გასაგები შეტყობინება აჩვენე.

### ცხოვრების ღირებულება

ძირითადად აჩვენე `Cost of Living Index` ქირის გარეშე. ხელმისაწვდომობისას დაამატე ქირის ინდექსი და `Cost of Living Plus Rent Index`. Numbeo-ს შემთხვევაში განმარტე საბაზო შედარება „ნიუ-იორკი = 100“. ინდექსი ფულადი თანხა არ არის და თვიურ ხარჯად არ უნდა გამოჩნდეს. სხვა პროვაიდერის განსხვავებული ბაზა ან მეთოდოლოგია ცხადად მიუთითე.

თუ სანდო წყარო ცალკე იძლევა თვიურ ფულად შეფასებას, ეს შეიძლება დამატებითი მაჩვენებელი იყოს ზუსტი მეთოდოლოგიითა და ოჯახის განსაზღვრებით. ინდექსიდან თვითნებური კურსით თანხა არ გამოითვალო. მხოლოდ ინდექსის არსებობა ფულადი თვიური ბიუჯეტის არსებობას არ ნიშნავს.

ბაზრის ინდექსი არ ჩაანაცვლებს ბრძანების `K`-ს და ქირის საშუალო არ ცვლის `E`-ს. მათი დანიშნულება საცხოვრებელი პირობების საორიენტაციო შეფასებაა.

### მონაცემის მდგომარეობები

გამოიყენე დამოუკიდებელი მდგომარეობები: იტვირთება, განახლებულია, შენახული მონაცემია, მოძველებულია, ხელითაა შეყვანილი, ნაწილობრივ ხელმისაწვდომია, ვერ მოიძებნა, კავშირი ვერ შედგა, პროვაიდერი არ არის კონფიგურირებული.

ქირასა და ინდექსს ჰქონდეს საკუთარი სტატუსი და მეტამონაცემები. ერთ-ერთი თუ ვერ მოიძებნა, მეორე არ დამალო. უცნობი თარიღი უცნობად დატოვე. `fetchedAt` — მიღების დრო — არ ჩათვალო `sourceUpdatedAt` — თავად მონაცემის განახლების დროდ. განახლებული ქეში ძველი ფასების ახლად გაზომვას არ ნიშნავს.

## 8 პროვაიდერის შერჩევა და ინტეგრაცია

პირველი შესაფასებელი კანდიდატია Numbeo-ს ოფიციალური API. ხელმისაწვდომ დოკუმენტაციაში არსებობს ქალაქების, ფასებისა და ინდექსების მოთხოვნები. API ფასიანია; 2026 წლის 28 ოქტომბერს გამოქვეყნებულ ყოველთვიურ ტარიფებში Basic მითითებული იყო 260 USD/თვე, გადასახადების გარეშე. ეს არის შესამოწმებელი საინფორმაციო ჩანაწერი და არა პროექტში ფიქსირებული ფასი ან შესყიდვის დავალება.

შეაფასე მინიმუმ კიდევ ერთი რეალური კანდიდატი, თუ მის ოფიციალურ დოკუმენტაციას მიაგნებ. Expatistan ან TravelTables შეიძლება იყოს შესასწავლი წყარო, მაგრამ მათი ვებგვერდის არსებობა ავტომატურად ხელმისაწვდომ და ნებადართულ API-ს არ ნიშნავს. ვერ დადასტურებული API, დაფარვა ან უფასო ტარიფი ასე მონიშნე; არ დაჰპირდე მომხმარებელს დაუდასტურებელ ინტეგრაციას.

`docs/providers.md`-ში შეადარე: ქალაქების დაფარვა; ცენტრის თვიური ქირა; საძინებლების კატეგორიები; ინდექსი და მისი ბაზა; თარიღები; ვალუტები; ფასი; კვოტა; API ავთენტიფიკაცია; ბრაუზერიდან დაშვება; მონაცემის შენახვის, ჩვენების, ექსპორტისა და გავრცელების უფლებები. იაფი ალტერნატივა მიიღე მხოლოდ თუ საჭირო მონაცემები და ნებადართული გამოყენება დასტურდება.

Numbeo-ს გამოყენების პირობები კრძალავს ნებართვის გარეშე ავტომატურ scraping-ს და ცალკე ზღუდავს სხვა API-ებით ან საჯარო მონაცემთა ნაკადებით ხელახალ გავრცელებას. ამიტომ არ ააწყო საჯარო უნივერსალური Numbeo proxy. განსაზღვრე აპის აუდიტორია და აუცილებელი ლიცენზია; server-side proxy თავისთავად გავრცელების უფლებას არ ქმნის. მოპოვებულ პირობებში დაუზუსტებელი ქეშირება, HTML-ში ჩაშენება ან ფაილად ექსპორტი დასაშვებად არ გამოაცხადო.

წესები შეამოწმე დანერგვის დღეს. არ გამოიყენო არაფორმალური scraper, CORS-ის გვერდის ასავლელი საჯარო proxy, პროვაიდერის გამოწვევების/შეზღუდვების გადალახვა ან მოხსენიება როგორც თითქოს ოფიციალური API იყოს.

### Numbeo-ს ადაპტერი

დოკუმენტაცია: `https://www.numbeo.com/api/doc.jsp`.

- ქალაქები დაამთხვიე `/api/cities`-ის რეალურ ID-ებს; არ გამოიგონო ID.
- ქირა მოიპოვე `/api/city_prices`-ით, ინდექსები `/api/indices`-ით; ნივთების იდენტიფიკაცია გადაამოწმე `/api/items`-ში.
- ამჟამინდელ ნიმუშში ცენტრის 1-საძინებლიანის `item_id` არის 26, 3-საძინებლიანის — 28; რეალურ სქემასთან მაინც შეამოწმე.
- ადაპტერში დააფიქსირე ზუსტი ქალაქის შესაბამისობა. სადაც მხარდაჭერილია, გამოიყენე `strict_matching=true` და `use_estimated=false`, რათა სხვა ქალაქის შეფასება შეუმჩნევლად არ დაბრუნდეს.
- გადაამოწმე პასუხის ქალაქი და ვალუტა. ფასისთვის გამოიყენე `average_price`; ინდექსისთვის შესაბამისი `cpi_index`, დამატებით `rent_index` და `cpi_and_rent_index`.
- ფასი მოითხოვე საჭირო ვალუტაში, თუ API იძლევა ამის შესაძლებლობას; ერთსა და იმავე პასუხს მეორედ არ გაუკეთო კონვერტაცია.

რეალური გასაღების არქონისას შექმენი სრული ადაპტერი და კონტრაქტის ტესტები დოკუმენტაციასთან შესაბამისი სინთეზური მაგალითებით. სატესტო ქალაქების ფასები ცოცხალ მონაცემებად არ ჩასვა მომხმარებლის ჩვეულებრივ რეჟიმში. საბოლოოდ დაწერე „რეალურ API-სთან კავშირი არ შემოწმებულა“, თუ გასაღებით მოთხოვნა რეალურად არ შეგისრულებია.

### ალტერნატიული რეჟიმები

სავალდებულოა ხელით შესატანი და ვალიდირებული JSON-იდან იმპორტის რეჟიმი. მონაცემს ჰქონდეს ქალაქი, მაჩვენებლის ზუსტი ტიპი, ვალუტა, წყაროს დასახელება/URL, წყაროს თარიღი თუ ცნობილია და შეყვანის დრო. ხელით შეტანილი მონაცემი „ავტომატურად მოპოვებულად“ არ მონიშნო.

შენახული ბაზრის მონაცემების ჩაშენება შეიძლება მხოლოდ შესაბამისი უფლებით. ასეთი მონაცემი გამოჩნდეს როგორც დათარიღებული ასლი და არა მიმდინარე live ფასი. უფლებების ან მონაცემის არქონისას აჩვენე ხელით შესავსები ცარიელი მდგომარეობა; შემთხვევითი ნიმუში რეალური ფასის ნაცვლად არ გამოიყენო.

## 9 ტექნიკური არქიტექტურა და Cloudflare

პირველ ეტაპზე შეადგინე მოკლე არქიტექტურული გადაწყვეტილება: რომელი მოთხოვნა სრულდება დამოუკიდებელი HTML-ით და კონკრეტულად რის გამო ხდება საჭირო სერვერული ნაწილი. პრიორიტეტია მინიმალური დამოკიდებულებები და ერთი გამოთვლის ბირთვი.

| ვარიანტი | გამოყენება | რა უნდა იყოს მზად |
| --- | --- | --- |
| ერთი HTML ფაილი | სრული ოფლაინ გამოთვლები; ხელით ან ნებადართული შენახული ასლით ბაზრის მონაცემები; live მონაცემები მხოლოდ უსაფრთხო და ნებადართული პირობებით | ერთ ფაილში ჩაშენებული სტილები, ლოგიკა, ნორმატიული მონაცემები და აუცილებელი რესურსები |
| HTML და მცირე Worker | პროვაიდერის საიდუმლო გასაღებით ავტომატური მონაცემები | იგივე UI და ბირთვი, დაცული API ადაპტერი, Cloudflare კონფიგურაცია და ინსტრუქცია |

ბრაუზერში შესრულებად კოდში საიდუმლო API გასაღების დამალვა შეუძლებელია. გასაღები არ ჩასვა HTML-ში, client bundle-ში, URL-ში, რეპოზიტორიაში ან localStorage-ში. მომხმარებელს „საკუთარი გასაღები ჩასვით HTML-ში“ უსაფრთხო სერვერული ინტეგრაციის ნაცვლად არ შესთავაზო. `file://`-დან მუშაობა და ინტერნეტთან კავშირი ცალკე გადაამოწმე; CORS მხარდაჭერა წინასწარ არ ივარაუდო.

თუ Numbeo ან სხვა secret-key API აირჩევა, რეკომენდებული მინიმალური სტრუქტურაა Cloudflare Workers Static Assets და Worker-ის `/api/market` მარშრუტი. React, Next.js, D1 ან სხვა დიდი კომპონენტი აუცილებლობის გარეშე არ დაამატო. მსუბუქი TypeScript/JavaScript და საჭიროებისას მცირე build სისტემა საკმარისია.

შეინარჩუნე ერთფაილიანი ოფლაინ გამოშვებაც, თუ იგი იმავე წყაროებიდან მიიღება ზედმეტი არქიტექტურის გარეშე. ონლაინ და ოფლაინ ვერსიების სამართლებრივი შედეგები უნდა ემთხვეოდეს. ოპერაციული სისტემა და ბრაუზერი წარმოადგენდეს მომხმარებლისთვის საკმარის გარემოს ოფლაინ ფაილის გასახსნელად; Node-ის დაყენება საბოლოო მომხმარებელს არ სჭირდებოდეს.

### Worker-ის მოთხოვნები

- API გასაღები შეინახე Cloudflare Secret-ში; `wrangler.jsonc`-ში მხოლოდ არასაიდუმლო პარამეტრები.
- შენი აპის მოთხოვნას ჰქონდეს ცნობილი შიდა ქალაქის ID და ნებადართული ვალუტა. მომხმარებლისგან arbitrary upstream URL არ მიიღო.
- მისამართი მიაბი მხოლოდ შერჩეულ პროვაიდერს. მონაცემთა პასუხი იყოს შეზღუდული აპისთვის საჭირო ველებით და შესაბამისი ლიცენზიით ნებადართულ აუდიტორიაზე.
- გამოიყენე შესვლის/წვდომის კონტროლი, თუ ლიცენზიისა და აუდიტორიისთვის საჭიროა. CORS და Origin შემოწმება ავთენტიფიკაციად არ ჩათვალო.
- დაიცავი კვოტა rate limiting-ით, მოთხოვნების გაერთიანებითა და ნებადართული ქეშით. ქეშის გასაღებში შეიტანე პროვაიდერი, ქალაქი, ვალუტა და სქემის ვერსია.
- TTL და ძველი მონაცემის გამოყენების ზღვარი იყოს კონფიგურირებადი და ლიცენზიასთან შესაბამისი. დასაშვებობის დადასტურების შემდეგ სამუშაო საწყისი TTL შეიძლება იყოს 24 საათი; ეს არ არის პროვაიდერისგან გარანტირებული უფლება.
- დაამუშავე timeout, 401/403, 429, 5xx, არასწორი JSON, არასრული მონაცემი და არასწორი ქალაქი. უსასრულო განმეორებითი მოთხოვნები არ გააგზავნო.
- სწრაფი გადართვისას წინა ქალაქის გვიან მოსულმა პასუხმა ახალი ქალაქი არ გადაწეროს; გამოიყენე გაუქმება ან მოთხოვნის იდენტიფიკატორი.
- ლოგებში არ ჩაწერო გასაღებები, ხელშეკრულებები, ოჯახის ასაკები, სახელები ან პირადი საფინანსო შეყვანა.

ფინანსური გაანგარიშება დარჩეს ბრაუზერში. გარე სერვისს ჩვეულებრივ სჭირდება მხოლოდ ქალაქი და ვალუტა. ოჯახის მონაცემების გაგზავნა საჭირო არ არის. მონაცემთა ბაზა და ანგარიშების რეგისტრაცია დაამატე მხოლოდ კონკრეტულად დასაბუთებული საჭიროებით.

### განთავსების პაკეტი

Cloudflare-ის ვარიანტს დაურთე `package.json`, lockfile, `wrangler.jsonc`, `.dev.vars.example`, `.gitignore`, აწყობის/ტესტის/განთავსების სკრიპტები და ქართული ინსტრუქცია. მაგალითის secret იყოს აშკარად ცარიელი ან ნიმუშური; რეალური საიდუმლო არქივში არ მოხვდეს.

მოამზადე გადამოწმებული ბრძანებები სუფთა გარემოდან ინსტალაციისთვის, ლოკალური გაშვებისთვის, ტესტისთვის, build-ისთვის და განთავსებისთვის. Workers-ის გზის შემთხვევაში ჩვეულებრივი ინსტრუმენტებია `wrangler dev`, `wrangler secret put` და `wrangler deploy`; საბოლოო ბრძანებები მიაბი რეალურ პროექტს და გადაამოწმე მიმდინარე დოკუმენტაციით.

განასხვავე სტატიკური ფაილების ატვირთვა და სერვერული ფუნქციების გამოქვეყნება. თუ Pages Functions აირჩევა, Cloudflare dashboard-ის ჩვეულებრივი drag-and-drop ატვირთვა Functions-ის განთავსების სრულ გზად არ აღწერო; ოფიციალური დოკუმენტაციით საჭიროა მხარდაჭერილი Wrangler/Git პროცესი. აირჩიე ერთი ძირითადი ონლაინ განთავსების გზა და ბოლომდე აღწერე.

რეალური ანგარიშისა და გასაღების გარეშე შეამოწმე რაც შესაძლებელია ლოკალურად და `dry-run` რეჟიმით. მომზადებული კოდი არ მონიშნო უკვე განთავსებულ საიტად.

## 10 ინტერფეისი და შედეგების წარმოდგენა

მთელი მომხმარებლის ინტერფეისი იყოს ქართულად, მარტივი და პროფესიული. ინგლისური დასახელებები დატოვე მხოლოდ წყაროს იდენტიფიკაციისთვის ან აუცილებელი ტერმინის განმარტებაში. შეინარჩუნე არსებული კალკულატორის სწრაფი გამოყენების იდეა, მაგრამ არ გადაიტანო მისი ყველა ნაბიჯი ან ვიზუალური ელემენტი აუცილებლობის გარეშე.

ძირითადი სამუშაო გზა:

1. ქვეყანა, ქალაქი და დაწესებულება; იქვე ქირის/ცხოვრების ღირებულების ბლოკი.
2. რეჟიმი, თანამდებობა, სპეციალური სტატუსი და საანგარიშო თვე/პერიოდი.
3. ოჯახი და შესაბამისი პირობები.
4. ფაქტობრივი ან დაგეგმილი ქირა, განათლება და სხვა არჩეული ხარჯები.
5. გასაგები შედეგი და დეტალური განმარტება მოთხოვნისამებრ.

მარტივ საწყის ხედში მხოლოდ აუცილებელი ველები გამოჩნდეს. იშვიათი შემთხვევები გაიხსნას დამატებითი პირობების განყოფილებაში. ველის შეცვლისას შედეგი განახლდეს ავტომატურად და არ დაიკარგოს სხვა შევსებული მონაცემები.

შედეგში განასხვავე:

- **ყოველთვიური სამივლინებო თანხა** — `S`, განმარტებით `H, A, K, C, D, E, T, G, F`.
- **ხარჯების ანაზღაურება** — განათლება, დაზღვევა და სხვა შესაბამისი ხარჯები; ფაქტობრივი ან დაგეგმილი თანხა და ზღვარი.
- **ქირისა და შეყვანილი განათლების ხარჯის შემდეგ დარჩენილი თანხა** — შესაბამისი მარტივი სცენარისთვის `S + educationReimbursement − G − educationExpense`.
- **ერთჯერადი დახმარება და ერთჯერადი ხარჯის დაბრუნება** — ცალკე კატეგორიებით.
- **წლიური ზღვარი** — მაგალითად დაზღვევაზე; არ ნიშნავს ავტომატურად მიღებულ თანხას.
- **ავანსი და დასაბრუნებელი ვალდებულება** — დამოუკიდებლად.
- **ბაზრის საინფორმაციო მაჩვენებლები** — წყაროსა და მდგომარეობის მითითებით.

„ხელფასი“, „ყველა ხარჯის შემდეგ“ ან „გარანტირებულად ხელზე ასაღები“ არ გამოიყენო, როცა მხოლოდ კონკრეტული კომპონენტები გაქვს დათვლილი. საკვები, კომუნალური და სხვა ყოველდღიური ხარჯები ნაშთიდან გამოკლებულად არ წარმოაჩინო, თუ ისინი შეყვანილი და გათვალისწინებული არ არის. უარყოფითი ნაშთი აჩვენე რეალურად, ნულამდე არ მოჭრა.

წლის ან მთელი როტაციის პროგნოზი დაეფუძნოს თვიურ განრიგს, ცნობილ პერიოდებსა და მონიშნულ ვარაუდებს. უცვლელი თვიური თანხის ×12 შეიძლება იყოს მკაფიოდ მონიშნული მარტივი სცენარი; ის განსხვავდება ფაქტობრივი საანგარიშო წლისგან. შვებულების თანხა ავტომატურ „მეცამეტე თვედ“ არ დაამატო შესაბამისი საფუძვლის შემოწმების გარეშე.

შეფასებისა და დოკუმენტირებული ხარჯის სტატუსები განასხვავე. დასადასტურებელი ხარჯის არსებობისას აჩვენე დასრულებული ქვეჯამი და ცალკე გაურკვეველი ნაწილი; არასრული საბოლოო ჯამი სრულად არ წარმოადგინო.

## 11 მონაცემთა კონტრაქტები

ხელმძღვანელმა განხორციელების დაწყებამდე შეათანხმოს საერთო სქემები. ქვემოთ მოცემული სახელები შიდა პროექტის კონტრაქტის მაგალითია და არ წარმოადგენს Numbeo-ს მზა პასუხს.

ნორმატიულ მონაცემებში ცალ-ცალკე შეინახე `missions`, `locations`, `positionProfiles`, `baseAmounts`, `costCoefficients`, `insuranceCaps`, `baggageCaps`, `dailyRates` და `sourceReferences`. სამართლებრივ მონაცემებს ჰქონდეს თავისი `rulesVersion`; ბაზრის მონაცემებს — დამოუკიდებელი განახლების სტატუსი.

ბაზრის ნორმალიზებული პასუხის მინიმალური შინაარსი:

```text
MarketData
  schemaVersion
  requestedLocationId
  resolvedLocation: city, countryCode, providerCityId, matchStatus
  provider: id, name, sourceUrl, attribution
  currency
  rent: metric, bedrooms, area, average, low, high, dataPoints,
        status, sourceUpdatedAt, fetchedAt
  indices: costOfLivingExcludingRent, rentIndex, costOfLivingPlusRent,
           baseline, status, sourceUpdatedAt, fetchedAt
  cache: state, expiresAt
  warnings[]
```

არარსებული მნიშვნელობები იყოს `null` შესაბამისი სტატუსით და არა `0`. პროვაიდერს თუ განახლების თვე/წელი აქვს, ზუსტი დღე არ გამოიგონო. თითოეული ველის წყარო და სემანტიკა შეინარჩუნე; სხვადასხვა პროვაიდერიდან შევსებული მაჩვენებლების შემთხვევაში წყარო მიუთითე თითოეულზე.

გამოთვლის პასუხში შეიტანე თანხასთან ერთად კომპონენტები, წესების ID-ები, გამოყენებული შეყვანები, ვალუტა, პერიოდი, შეცდომები/გაფრთხილებები და სისრულის მდგომარეობა. UI-მ იმავე პასუხი გამოიყენოს ეკრანისა და ბეჭდვისთვის, რათა ისინი ერთმანეთს არ აცდეს.

შეინახე შესადარებელი ნედლი ამონაწერები დეველოპერულ პროექტში. აპის საჯარო static-assets დირექტორიაში შემთხვევით არ მოხვდეს დედანი სამუშაო დოკუმენტები, ტესტის საიდუმლოებები ან ზედმეტი მონაცემები. ნორმატიული JSON-ის იმპორტისას შეამოწმე სქემა, მითითებები, რიცხვების ტიპები, დუბლირებული ID-ები და გაურკვეველი მონაცემები.

## 12 ტესტები და მიღების კრიტერიუმები

ტესტები უნდა მოიცავდეს მონაცემების სისწორეს, ფინანსურ ლოგიკას, ქალაქების შესაბამისობას და ორივე გამოსაშვები რეჟიმის ქცევას. მარტო build-ის დასრულება მიღებისთვის საკმარისი არ არის.

### ეტალონური ფინანსური მაგალითები

ქვემოთ მოცემული მარტივი `D = 1000`, `T = 200` მაგალითები ამოწმებს ქირის ფუნქციას იზოლირებულად. ისინი რომელიმე მისიის ფაქტობრივი მონაცემები არ არის.

| შემთხვევა | G | F | S |
| --- | ---: | ---: | ---: |
| ქირა არ არის | 0 | 0 | 800 |
| 0 < G < T | 100 | 200 | 1000 |
| G = T უწყვეტი ინტერპრეტაციით | 200 | 200 | 1000 |
| სხვა მოსამსახურე | 400 | 300 | 1100 |
| სხვა მოსამსახურე ზღვარზე მაღალი ქირით | 1000 | 400 | 1200 |
| ხელმძღვანელი | 400 | 360 | 1160 |
| ხელმძღვანელი ზღვარზე მაღალი ქირით | 1000 | 600 | 1400 |

მოწოდებული ვენის მონაცემებზე დაფუძნებული სრული თვის საკონტროლო სცენარი: `H = 3100 EUR`, `A = 65%`, `K = 2.06`, `E = 21%`, ორი უფლებამოსილი ოჯახის წევრი, არახელმძღვანელი, `G = 1500 EUR`. შუალედური დამრგვალების გარეშე შედეგებია: `D = 4732.03`, `T = 993.73`, `F = 1246.86`, `S = 4985.16` — ეკრანზე ორ ათწილადამდე. ერთი უფლებამოსილი ბავშვის დასაშვები განათლების ხარჯი 1000 EUR იძლევა 938 EUR ანაზღაურებას და ქირისა და განათლების შემდეგ 3423.16 EUR ნაშთს. ეს არის ტესტის სცენარი და არა ვინმეს პერსონალური გაანგარიშება.

დამატებით გადაამოწმე:

- `P = 1000 EUR` → განათლების ანაზღაურება 938 EUR; `P = 1000 USD` → 950 USD; `P = 0`, ზუსტად `L`, რამდენიმე ბავშვი და არაუფლებამოსილი ხარჯი.
- საკომისიო 300, ქირა 1500 → 150 არახელმძღვანელისთვის და 240 ხელმძღვანელისთვის; საკომისიო 4000 და ქირა 1500 → ანაზღაურება ერთთვიან ქირას არ აღემატება.
- ბარგის ხარჯი 600 და ლიმიტი 1650 → 600; უკვე გამოყენებული ლიმიტი და ოჯახის რამდენიმე მოთხოვნა.
- სინთეზური დადასტურებული დღიური ნორმა 60 შესაბამის ვალუტაში და ორი დასათვლელი წევრი → პირველადი მოწყობა 4320; გამორიცხული სტატუსი 10%-ს არ ზრდის.
- არასრული თვის ფუნქცია შეთანხმებული პოლიტიკით: სრული განაკვეთი 1000, 31-დღიან თვეში 15 დღე → 483.87; ნაკიანი თებერვლის 29 დღიდან 15 დღე → 517.24.
- ასაკის ყველა საზღვარი, განსაკუთრებით 18/19, 24/25, 64/65, 69/70 და 70-ზე უფროსი; ცარიელი ასაკი და უცნობი ტარიფი.
- შუა თვეში ქირის/ოჯახის ცვლილება; ორმაგი დანამატის აკრძალვა; მხარდაჭერის მიმღების ყოფნის დღეები.
- ქირის საზღვრები: ნულთან ახლოს დადებითი ქირა, `G = T`-ის ორივე მხარე და დამატებითი ანაზღაურების ზღვარი — სხვა მოსამსახურისთვის `G = 3T`, ხელმძღვანელისთვის `G = 3.5T`.
- №2 და №3 რეჟიმის განსხვავება, ხელმძღვანელის სტატუსი და სპეციალური ადმინისტრაციული მენეჯერი.
- ავანსის გაცემა/დაბრუნება წლიურ შემოსავალს ხელოვნურად არ ზრდის.

### მონაცემების ტესტები

გადაამოწმე ყველა ამოღებული რიცხვი და წყაროს შესაბამისობა. თითო ნორმატიული ჩანაწერი იყოს სწორი ტიპის, ვალუტისა და წყაროს მქონე. არ დაუშვა წაშლილი სტრიქონის არჩევა, არასწორი მასივის ინდექსი ან ჩუმად ნულით ჩანაცვლებული ლიმიტი.

აუდიტის ცხრილის ყველა შესწორებას მიაბი ტესტი: ირანი, ოდესა/კიევი, ლიონი, შტუტგარტი, ცალკე ნატო და ნიუ-იორკის სხვადასხვა დაწესებულება. სადაც ნორმატიული მონაცემი აკლია, ტესტი მოითხოვდეს განმარტებულ „დაუდგენელ“ მდგომარეობას და არა გამოგონილ სწორ რიცხვს.

### ინტეგრაციისა და ბრაუზერის ტესტები

- ერთი HTML იხსნება `file://`-ით და გამოთვლები მუშაობს გათიშული ინტერნეტით; გარე რესურსის დაბლოკვა ბირთვს არ აფუჭებს.
- ქვეყნის/ქალაქის ცვლილებაზე ბაზრის ბლოკი ჩანს იმავე ფორმაში; არასწორი ქალაქის პასუხი უარყოფილია.
- API-ის უქონლობა, timeout, 401, 403, 429, 5xx, არასრული JSON, ქირის არქონა, ინდექსის არქონა და ძველი ქეში სწორ მდგომარეობებს იძლევა.
- მხოლოდ ფასის განახლება ოფიციალურ `K`, `E`, `H` და მომხმარებლის ფაქტობრივ ქირას არ ცვლის.
- ხელით შეტანილი ქირა და პროვაიდერის ფასი მკაფიოდ განსხვავდება; ფასის სცენარში გადატანა მხოლოდ მომხმარებლის მოქმედებით ხდება.
- სწრაფი ქალაქის შეცვლისას ძველი პასუხი ახალს არ გადაწერს; ქეში ქალაქსა და ვალუტას არ ურევს.
- JSON იმპორტში არასწორი სქემა, მავნე ტექსტი ან უცნობი ვალუტა გასაგებად უარყოფილია.
- მომხმარებლისა და პროვაიდერის ტექსტი HTML/JavaScript-ად არ სრულდება.
- ქსელის ჩანაწერებში არ ჩანს ოჯახის ან პირადი ფინანსების მონაცემები; build-ში და არქივში არ არის საიდუმლო გასაღები.
- ეკრანისა და PDF/ბეჭდვის თანხები ემთხვევა; ქართული ასოები, გრძელი მისიის სახელი და მრავალშვილიანი სცენარი არ იჭრება.
- ოფლაინ და Cloudflare ვერსიები ერთსა და იმავე შეყვანაზე ერთსა და იმავე ფინანსურ შედეგს იძლევა.
- სუფთა გარემოში მუშაობს დოკუმენტირებული install, test, build და deployment dry-run. რეალური live შემოწმება ცალკე აღირიცხება მხოლოდ შესრულების შემთხვევაში.

გამოიყენე მიზანშეწონილი ინსტრუმენტები, მაგალითად unit tests და Playwright. ტესტების რაოდენობაზე მეტად მნიშვნელოვანია არსებითი შემთხვევებისა და სამართლებრივი საზღვრების დაფარვა.

## 13 შესრულების ეტაპები

**პირველი ეტაპი — წყაროები და აუდიტი.** ერთდროულად დაიწყოს სამართლებრივი შესწავლა, ძველი HTML-ის მონაცემების აუდიტი და API/არქიტექტურის კვლევა. UI-ის აგენტმა შეისწავლოს არსებული ნაკადი და მოამზადოს მოკლე გადაწყვეტა; სატარიფო ცხრილები მისმა აგენტმა თავიდან არ აკრიფოს.

**მეორე ეტაპი — საერთო კონტრაქტები.** ხელმძღვანელმა შეაჯამოს წესების რეესტრი, მონაცემთა სქემები, უცნობი საკითხები და არჩეული ტექნიკური გზა. ტესტის აგენტმა დააფიქსიროს დამოუკიდებელი ეტალონები. UI-სა და ბირთვის შეთანხმება ჩაიწეროს კოდში ან სქემაში.

**მესამე ეტაპი — განხორციელება.** პარალელურად შეიქმნას გამოთვლების ბირთვი, UI და მონაცემთა ადაპტერი შეთანხმებული კონტრაქტებით. დოკუმენტაციის ამონაწერები და ფინანსური მონაცემები ერთ წყაროდ დარჩეს; frontend-ში მათი ცალკე ასლები ხელით არ გამრავლდეს.

**მეოთხე ეტაპი — ინტეგრაცია და გამოსწორება.** გაიაროს მონაცემთა, ფორმულების, წვდომის, ქსელის და ვიზუალური შემოწმება. აღმოჩენილი ფინანსური შეცდომა გასწორდეს; წინააღმდეგობა მხოლოდ README-ში არ გადაიმალოს.

**მეხუთე ეტაპი — გამოშვება.** ააგე რეალური ერთფაილიანი შედეგი და საჭირო ონლაინ პაკეტი. არქივი შექმენი საბოლოო, შემოწმებული წყაროდან. ტესტის ანგარიში მიუთითებდეს რომელი შემოწმება შესრულდა, რომელი ვერ შესრულდა და კონკრეტულად რატომ.

გარე გასაღების ან ერთი საკითხის განმარტების არქონისას დამოუკიდებელი სამუშაო გააგრძელე. თუ რომელიმე დაუზუსტებელი წესი გავლენას ახდენს თანხაზე, აპმა შესაბამისი ნაწილი მიუთითოს როგორც დაუდგენელი ან სცენარული; შედეგი დაზუსტებულად არ გაასაღოს.
